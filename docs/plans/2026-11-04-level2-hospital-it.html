Full IT for a Level 2 hospital: OpenMRS as the EMR, hospital-fabric as the operating layer Draft v2

2026-11-04 · gmackie/hospital-fabric @ main (632106f) · Path A on celld · reference demos on labnuc and Cloudflare · issues HF-13 (Phase R), HF-14…HF-22 (Phases 0–8)

Recommendation: Run the hospital on a pinned set of open-source systems of record (OpenMRS O3, OpenELIS, Orthanc/OHIF, OpenBoxes, an ERP, DHIS2) hosted on site. hospital-fabric is the only component that moves data between them. It also owns capacity, downtime, device and utility visibility.

Fill clinical gaps by building OpenMRS modules, never by putting clinical records in hospital-fabric. Nothing touches a real patient until the Phase 1 security work and the Phase 7 downtime exercises pass.

Runtime: hospital-fabric is one Workers-API bundle. At a hospital it runs on a celld fleet beside the containerized products. In the cloud the same bundle runs on Cloudflare Workers. The two reference demos are those two roles: hospital.mackie.house on labnuc is the hospital site, and hospital.gmac.io on Cloudflare is the cloud tier.

Planning assumption to confirm: "Level 2" means a WHO-style first-referral or district hospital: emergency care, outpatients, general wards, maternity with caesarean capability, one or two theatres, a small HDU, a general lab with blood transfusion, X-ray and ultrasound, a pharmacy and stores. The design assumes unreliable WAN and power, which is the scenario this repo already models.

If you mean a US Level II trauma center, OpenMRS is the wrong EMR. ONC certification, HL7v2-heavy device and billing interfaces, and a trauma registry dominate that case, and the plan would change substantially. A WHO EMT Type 2 field hospital keeps this architecture but swaps the network and power sections for deployable kits.

Scope

Goals

  • Every department has a named system of record and a tested workflow
  • One patient identity across EMR, lab, imaging, pharmacy and billing
  • Clinical work continues on the LAN during WAN loss, and on paper during total IT loss, with tested back-entry
  • Real authentication, role-based access, emergency override, tamper-evident audit
  • Statutory reporting (DHIS2 / HMIS) without manual re-entry
  • Reproducible, signed, offline-installable deployment with tested restore

Non-goals

  • Writing a new EMR or storing clinical records in hospital-fabric
  • Writing to another product's database (supported APIs only)
  • Controlling medical devices, pumps, ventilators or alarms
  • Clinical decision support beyond critical-result routing (it would become regulated device software)
  • A second integration engine alongside hospital-fabric for the same flows
  • Cloud dependency for any bedside workflow

Two deployments, one bundle

What celld means for the design

From celld docs at v0.6.3 (released 2026-10-21; the repo pins 0.6.2): docs/limitations.md, guarantees.md, cloudflare-compat.md, services/containers.md.

celld behaviorDesign consequence
Workers, Durable Objects, D1, Queues, Workflows, cron and R2 are supported; Hyperdrive, Cache and tail are notOne bundle for both runtimes, limited to the shared API set. Both smoke suites (smoke:celld, smoke:workerd) gate every change
Exactly one node serves a cell; every activation advances a fencing epochModel each destination connector as one Durable Object cell. That gives single-writer delivery and fencing natively, which PRODUCTION.md item 6 currently lists as open work
Node leases live 10 s and renew through the bucket; a node that loses its lease fences itself and exitsThe bucket must be on site. With R2 as the bucket, a WAN cut stops hospital-fabric within seconds, defeating the offline-first goal
Qualified stores are S3, R2, Tigris, GCS and Azure. MinIO passes celld diagnose but is not production-qualified (use RELEASE.2025-09-07 or later)The labnuc demo uses pinned MinIO, explicitly labelled unqualified. Qualifying a production on-site store is a tracked Phase 1 risk
A single-node fleet waits for the bucket on every write; two or more nodes acknowledge after a peer fsyncThe demo can run on one node. A real site runs 2–3 nodes, and failover can only be shown with a second node (for example gmacko-mini over Tailscale)
No TLS; peer traffic is plaintext; the internal operator API is unauthenticatedCaddy in front; internal listener on Tailscale or a server VLAN, never exposed
Containers are experimental with ephemeral disksOpenMRS, OpenELIS and their databases stay in Podman under systemd beside celld, not inside it
One application per fleet; pre-1.0; some upgrades required stopping the whole fleethospital-fabric is the fleet's only app. Upgrades go through the acceptance suite and a downtime window

Infrastructure baseline

Network zones

  • Clinical: workstations, tablets, printers
  • Servers: on-site cluster; reachable only from clinical and operator zones
  • Devices: analyzers, modalities, sensors; isolated, gateway-only
  • Admin: finance and HR
  • Management: switches, UPS, out-of-band access
  • Guest: internet only, never routed inward

Power, time, comms

  • Online UPS for core switches, servers and downtime print stations; generator and solar transfer tested monthly
  • Local NTP and DNS: WAN loss must not break name resolution, certificates or login
  • Redundant core switching; ward access switches on UPS
  • Two WAN links where available; VPN for remote support and off-site backup
  • LAN VoIP and radios as independent communication paths

Mitigations
  • Wrong-patient results: correlate on stable order identifiers only, never on patient alone (already the rule in REAL-SERVICES.md); ambiguous matches go to the exception queue.
  • Scope growth: every new department need goes through the fit-gap; non-goals are enforced in review.
  • O3 feature gaps: the Phase 0 hands-on test turns unknowns into estimates before committing; upstream modules where possible to share maintenance.
  • Untested restore: restore drills are a Phase 1 exit gate and repeat quarterly.
  • Staff adoption: clinicians in every walkthrough, super-users per department, phased waves.
  • Two senders: one integration owner per flow, recorded in the component registry and checked at startup.
  • Unqualified on-site bucket: run celld diagnose on every node start (celld enforces it) and in CI; drill bucket restore; evaluate production on-site stores as a Phase 1 task.
  • celld pre-1.0 changes: pin exact releases; re-run the full acceptance suite before upgrading; keep the bundle runnable on workerd as the fallback runtime.
  • labnuc capacity: the demo runs OpenMRS and OpenELIS only at first; OpenBoxes, DHIS2 and Orthanc are added one at a time with memory measured, or run on hetzner-master and are labelled "not on site".
  • Security breach: threat model, segmented network, OIDC with MFA, audit chain, patch cadence, pen test before go-live.
